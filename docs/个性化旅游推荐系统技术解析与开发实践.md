# 从毕业设计到可运行系统：个性化旅游推荐系统技术解析与开发实践

> 本文以一个真实的毕业设计项目为例，介绍如何使用 Vue 3、Spring Boot、MySQL、Redis 和推荐算法，构建一个包含用户端、管理端和后端服务的全栈旅游系统。希望这篇文章能帮助正在做课程设计、毕业设计或全栈项目的同学理解：一个项目不只是“把页面做出来”，还要考虑数据建模、权限、缓存、算法、异常处理和部署配置。

## 一、项目是什么

这个项目是一个前后端分离的个性化旅游推荐系统，项目代号为 Travel System，用户端界面使用 WayStar 品牌。

系统围绕以下业务闭环展开：

1. 用户浏览景点、城市和旅游内容。
2. 用户通过收藏、点击、停留等行为形成偏好数据。
3. 推荐服务根据显式偏好和隐式行为返回景点。
4. 用户选择景点、出发地和出行方式后，系统生成旅游路线。
5. 管理员通过管理端维护景点、城市、标签、轮播图和用户数据。
6. 管理端通过 RBAC 权限和操作日志实现后台治理。

项目不是单一的 CRUD 示例，而是把内容管理、用户系统、推荐系统、路线规划和后台运营放在了同一个业务场景中。

## 二、整体架构

项目采用典型的前后端分离架构：

```text
┌────────────────────┐       HTTP/JSON        ┌────────────────────────┐
│ 用户端 homepage     │ ────────────────────▶ │                        │
│ Vue 3 + TypeScript  │                       │ Spring Boot 后端        │
└────────────────────┘                       │                        │
                                             │ REST API                │
┌────────────────────┐       HTTP/JSON        │ JWT / 权限拦截           │
│ 管理端 dashboard     │ ────────────────────▶ │ 推荐 / 路线 / AI 服务     │
│ Vue 3 + TypeScript  │                       │ Redis 缓存 / 异步线程池   │
└────────────────────┘                       └───────────┬────────────┘
                                                         │
                                      ┌──────────────────┼──────────────────┐
                                      ▼                  ▼                  ▼
                                  MySQL 8             Redis 7          高德 / DeepSeek
```

仓库主要目录如下：

```text
TravelSystem/
├── backend/
│   ├── python/                 # 数据采集和图片抓取脚本
│   ├── springProject/          # Spring Boot 后端
│   └── sql/                    # 建表、初始化和索引脚本
├── frontend-apps/
│   ├── homepage/               # 用户端
│   └── dashboard/              # 管理端
├── docs/                       # 开发、部署和设计文档
├── package.json                # 根目录工具依赖
└── README.md
```

后端代码按照 Controller、Service、Mapper、Entity、DTO 等层次组织；前端按照页面、组件、路由、状态管理和 API 模块组织。这种分层方式虽然不是唯一方案，但对于毕业设计来说容易理解、便于测试，也方便在答辩时说明请求的完整链路。

## 三、技术栈与每项技术的作用

### 1. Java 21

后端使用 Java 21，并在 Maven 配置中通过 `<java.version>21</java.version>` 指定编译版本。

Java 在项目中承担业务服务、算法计算、数据库访问和第三方 API 调用等工作。路线规划中的模拟退火、推荐排序、缓存封装和权限校验也都在 Java 服务层完成。

### 2. Spring Boot 3.5.x

后端当前 `pom.xml` 使用 Spring Boot `3.5.13`。Spring Boot 负责：

- 启动应用和自动配置；
- 管理依赖和 Bean；
- 提供 Web MVC 能力；
- 读取 `application.yml` 配置；
- 组合 Spring Web、Validation、Mail、AOP 等模块。

项目使用 Jakarta 命名空间，因此需要注意 Spring Boot 3 与 Spring Boot 2 的依赖和 API 并不完全兼容。

### 3. Maven 与 Maven Wrapper

后端通过 `backend/springProject/pom.xml` 管理 Java 依赖，目录中还提供了 `mvnw` 和 `mvnw.cmd`。

Maven Wrapper 的价值是让团队尽量使用项目指定的 Maven 版本，而不是完全依赖本机安装的 Maven。Windows 可以使用：

```powershell
cd backend\springProject
.\mvnw.cmd spring-boot:run
```

Linux 或 macOS 可以使用：

```bash
cd backend/springProject
bash mvnw spring-boot:run
```

如果直接执行 `./mvnw` 报权限错误，可以使用 `bash mvnw`，或者为脚本补充执行权限。

### 4. Lombok

项目使用 Lombok 简化 Java 样板代码，常见注解包括：

- `@RequiredArgsConstructor`：生成构造器，配合构造器注入；
- `@Slf4j`：生成日志对象；
- `@Data`、`@Builder` 等：减少实体和 DTO 的 getter、setter、构造器代码。

当前项目显式使用 Lombok `1.18.42`，并且在 Maven 编译器插件的 `annotationProcessorPaths` 中使用同一版本。显式统一版本很重要，否则可能出现依赖版本和注解处理器版本不一致，或者在较新 JDK 下编译失败。

### 5. Spring Web MVC

后端通过 `@RestController` 暴露 REST API，使用 `@RequestMapping`、`@GetMapping`、`@PostMapping` 等注解定义接口。

主要控制器包括：

- `UserHomeController`：用户注册、登录、个人资料和用户侧能力；
- `AttractionHomeController`：景点浏览；
- `RecommendationController`：推荐和行为埋点；
- `RoutePlanController`：路线规划；
- `AiChatController`：AI 旅游助手；
- `DashboardController`：运营数据看板；
- 多个 `Admin` 控制器：管理员、景点、城市、标签、角色和权限管理。

接口统一使用 DTO 接收请求和返回结果，避免直接把数据库实体作为所有接口的输入输出对象。

### 6. MyBatis-Plus

项目使用 MyBatis-Plus `3.5.9`，并使用 `mybatis-plus-spring-boot3-starter` 适配 Spring Boot 3。

MyBatis-Plus 主要解决两类问题：

1. 对常规单表增删改查提供通用能力；
2. 在保留 MyBatis 灵活 SQL 的同时，减少重复代码。

项目中的 `entity` 目录保存数据库实体，`mapper` 目录保存 Mapper 接口，复杂查询可以通过自定义 Mapper 方法完成。例如推荐系统需要按时间窗口统计用户行为，管理看板需要统计趋势、分布和 TOP 数据，这些场景不适合只依赖简单 CRUD。

项目还使用了：

- `mybatis-plus-jsqlparser`：支持相关 SQL 解析能力；
- `mybatis-plus-generator`：用于代码生成相关能力。

### 7. MySQL 8

MySQL 保存系统的持久化业务数据，主要包括：

- 用户、管理员和用户资料；
- 景点、城市、景点类型和标签；
- 用户收藏、浏览行为和偏好；
- 路线及景点关系；
- 轮播图；
- 管理员角色、权限和关联关系；
- 操作日志和统计数据。

表设计中使用了逻辑删除字段。MyBatis-Plus 的配置将 `deleted=1` 视为已删除，`deleted=0` 视为正常数据。逻辑删除可以保留历史记录，适合景点、用户和管理数据这类需要审计或恢复的场景。

数据库脚本位于 `backend/sql`，常用文件包括：

- `all.sql`：完整初始化脚本；
- `travel_system.sql`：主要建表和初始化脚本；
- `performance_indexes.sql`：性能索引脚本；
- 其他数据更新脚本：用于城市、景点图片等数据维护。

### 8. Redis

Redis 在项目中不是主数据库，而是作为缓存和短期状态存储使用。典型用途包括：

- 景点列表和景点详情缓存；
- 热门景点缓存；
- 首页推荐缓存；
- 路线规划结果缓存；
- AI 会话历史；
- 缓存重建锁和空值标记。

项目中的 `CacheClient` 封装了缓存旁路模式，并处理了几个常见问题：

- **缓存穿透**：对不存在的数据缓存短期空值；
- **缓存击穿**：对热点 Key 的重建使用互斥控制；
- **缓存雪崩**：在 TTL 上增加随机抖动，避免大量 Key 同时过期；
- **缓存预热**：启动或定时加载景点 ID 集合，减少明显无效查询。

缓存不是“加上 Redis 就一定变快”。缓存 Key 的设计、数据更新时机、过期策略和一致性都需要结合业务一起考虑。

### 9. Vue 3

用户端和管理端都使用 Vue 3。Vue 负责：

- 组件化构建页面；
- 响应式更新；
- 表单和列表交互；
- 路由页面切换；
- 与后端 API 联调。

用户端页面包括推荐首页、探索、热门城市、景点详情、路线规划和个人中心；管理端页面包括运营看板、用户、景点、城市、标签、轮播图、管理员、角色权限和操作日志。

### 10. TypeScript

两个前端应用都使用 TypeScript。TypeScript 的主要价值不是让代码“自动正确”，而是让接口数据、组件参数和状态结构更容易被检查。

例如，前端 API 模块可以定义请求和响应类型，减少把分页响应、用户信息或路线结果误当成其他对象使用的风险。对于毕业设计，TypeScript 也能帮助展示前端工程化能力。

### 11. Vite

Vite 是两个前端应用的开发服务器和构建工具，启动速度快，适合 Vue + TypeScript 项目。

两个应用都提供以下脚本：

```bash
pnpm dev
pnpm build
pnpm preview
```

构建脚本会先执行 `vue-tsc -b` 进行类型检查，再执行 Vite 构建。

### 12. pnpm

项目的前端依赖使用 pnpm 管理。仓库 README 建议使用 Node.js 18+ 和 pnpm 8+；各前端目录中的锁文件使用 `lockfileVersion: '6.0'`，因此建议优先使用 pnpm 8，降低锁文件兼容问题。

安装依赖：

```bash
cd frontend-apps/homepage
pnpm install

cd ../dashboard
pnpm install
```

### 13. Element Plus

Element Plus 是 Vue 3 的组件库，项目使用它实现：

- 登录和注册表单；
- 表格、分页和弹窗；
- 表单校验；
- 消息提示；
- 管理端布局和数据管理界面。

管理端还注册了 Element Plus Icons Vue，用户端和管理端都使用 Font Awesome 图标资源。

### 14. Pinia 与持久化插件

Pinia 用于管理前端共享状态。用户端的用户信息、收藏状态和景点类型等内容不适合完全依赖单个组件维护，因此通过 Store 统一管理。

用户端还使用 `pinia-plugin-persistedstate`，用于在页面刷新后保留部分状态。需要注意：持久化状态并不等于安全存储，敏感令牌仍应结合合理的 Cookie、过期时间和服务端校验策略。

### 15. Vue Router

Vue Router 负责用户端和管理端的页面路由。用户端通过路由元信息标识需要登录的页面，路由守卫会在进入个人中心等页面前检查登录状态。

路由守卫适合改善用户体验，但不能代替后端鉴权。真正的权限判断必须在服务端完成，因为浏览器端代码和路由都可以被用户修改。

### 16. Axios

Axios 被封装成前端统一请求模块，负责：

- 配置 API 基础地址；
- 自动添加 Authorization 请求头；
- 统一处理响应结构；
- 统一处理 401、403、404、500 等错误；
- 文件上传和进度回调。

这样做可以避免每个页面重复编写登录态处理和错误提示逻辑。

### 17. ECharts

ECharts 主要用于管理端运营看板，将后端统计数据转换成趋势图、分布图和排行图，帮助管理员查看用户、景点和行为数据。

图表组件的关键不只是画图，还包括：

1. 后端返回稳定的数据结构；
2. 前端处理空数据和异常数据；
3. 时间范围、分页和筛选条件保持一致；
4. 大数据量场景下避免一次性返回所有明细。

### 18. Spring Validation

后端 DTO 使用 Jakarta Validation 对请求参数进行基本校验，例如必填字段、长度、数值范围和集合约束。校验应该放在接口边界，避免非法数据进入业务层和数据库。

不过，参数校验只能解决格式问题，不能替代业务校验。例如“管理员是否拥有修改某个资源的权限”仍然需要在权限逻辑中判断。

### 19. JWT、Spring Security 与 RBAC

项目使用 JWT 传递登录身份，应用配置为无状态会话。登录成功后，前端在后续请求中携带 Bearer Token，后端从 Token 中解析用户或管理员身份。

后台权限采用 RBAC（Role-Based Access Control，基于角色的访问控制）模型：

```text
管理员 ── 多对多 ── 角色 ── 多对多 ── 权限
```

管理员权限拦截器会检查：

1. 是否提供 Bearer Token；
2. Token 是否有效和未过期；
3. Token 是否属于管理员；
4. 管理员是否拥有接口要求的权限；
5. 将管理员信息和权限放入请求上下文。

密码存储使用项目中的 PBKDF2 工具进行加盐哈希；Spring Security 同时提供了 BCrypt `PasswordEncoder` Bean。学习时要区分“密码哈希”和“JWT 签名”：前者用于保存密码，后者用于证明 Token 没有被篡改。

### 20. Spring AOP

项目通过 AOP 实现操作日志切面。只要方法添加 `@OperationLog` 注解，切面就可以在方法执行前后收集：

- 操作类型和操作对象；
- 管理员 ID；
- 请求 IP；
- 方法参数或返回结果中的对象 ID；
- 成功或失败信息；
- 执行耗时。

AOP 适合处理这种横切关注点，可以避免在每个管理接口中手写重复日志代码。

### 21. springdoc-openapi

项目使用 springdoc-openapi 生成 OpenAPI 文档，后端启动后可以访问：

```text
http://localhost:8080/swagger-ui/index.html
```

Swagger UI 适合调试接口、查看请求参数和响应结构，也方便前后端联调。生产环境是否开放 Swagger，需要根据部署环境和安全策略决定。

### 22. OkHttp、SSE 与 AI 对话

AI 旅游助手通过 OkHttp 调用兼容 OpenAI 风格的聊天接口，并使用 Server-Sent Events（SSE）将流式内容推送到浏览器。

实现流程如下：

1. 前端发送用户问题和会话 ID；
2. 后端从 Redis 读取会话历史；
3. 后端补充旅游助手系统提示词和本轮用户消息；
4. OkHttp 以流式模式调用 AI 服务；
5. 后端接收内容片段并通过 `SseEmitter` 推送给前端；
6. 流结束后，将完整助手回复写回 Redis，并设置会话过期时间。

SSE 比一次性等待完整响应更适合聊天场景，因为用户可以边生成边看到内容。它是单向推送；如果需要双向实时通信、在线协作或复杂连接管理，可以进一步研究 WebSocket。

### 23. Python 数据脚本

`backend/python` 目录包含城市和景点数据处理、图片抓取等脚本。Python 在这个项目中不是后端在线服务，而是数据准备和运营辅助工具。

这种职责划分很常见：

- Java 服务负责稳定的在线 API；
- Python 负责一次性或定时的数据清洗、采集和转换；
- MySQL 保存最终可供业务使用的数据。

数据采集脚本需要遵守目标网站的服务条款、robots 规则和法律要求，并控制请求频率，不能把“能抓到”当成“可以随意抓取”。

### 24. 其他前端依赖

项目还使用了几项面向具体交互场景的前端依赖：

- **Sass / sass-embedded**：管理端和用户端使用 Sass 编写样式，支持变量、嵌套和模块化组织。Sass 只负责样式预处理，不会替代 Vue 组件。
- **Swiper**：用户端轮播图和滑动展示使用 Swiper，适合移动端和触摸交互。
- **md-editor-v3**：根项目和用户端包含 Markdown 编辑器依赖，可用于富文本或 Markdown 内容编辑。是否启用某个编辑页面，应以当前页面代码为准。
- **js-cookie**：前端通过它读取和删除登录 Cookie，配合 Axios 请求拦截器携带身份令牌。
- **@vue/runtime-dom**：Vue 在浏览器 DOM 环境中的运行时实现，通常由 Vue 组件运行所需。

### 25. 其他后端依赖

- **JJWT**：由 `jjwt-api`、`jjwt-impl` 和 `jjwt-jackson` 组成，用于创建和解析 JWT。API 与运行时实现分开声明，是 Java 生态中常见的依赖组织方式。
- **MySQL Connector/J**：MySQL JDBC 驱动，使 Spring Boot 和 MyBatis-Plus 能够通过 JDBC 连接 MySQL。
- **Commons Pool2**：提供对象池能力，项目的 Redis 连接池配置会使用相关能力管理连接资源。

- **Spring Boot Configuration Processor**：为自定义配置属性生成元数据，帮助 IDE 提示 `application.yml` 中的配置项。
- **Spring Mail**：提供邮件发送能力，项目用于邮箱验证码等场景。
- **Spring AOP 和 Spring Validation**：前者实现操作日志等横切逻辑，后者校验请求 DTO，两者分别解决“通用行为复用”和“输入边界校验”问题。

## 四、核心业务是怎样实现的

### 1. 个性化推荐

推荐服务不是直接随机返回景点，而是经过“候选召回—行为统计—Java 排序—分页返回”的过程。

#### 显式偏好

用户可以在偏好设置中选择景点类型等内容，系统将其保存为用户偏好。

#### 隐式行为

系统记录用户的点击和停留行为。`impression` 展示事件目前不直接入库，`stay` 事件会过滤过短停留，避免把误触和快速离开当成有效兴趣。

#### 冷启动和成熟阶段

项目通过配置区分不同阶段的权重：

- 冷启动：偏好权重较高，同时混入热门内容；
- 行为积累后：根据行为窗口内的统计结果提升个性化比例；
- 用户画像：由显式偏好和隐式行为共同组成。

这种设计解决了“新用户没有行为数据”的冷启动问题，也避免了“只看热门内容”导致推荐缺少个性化的问题。

#### 超时和缓存

推荐请求使用独立的异步执行器，并设置超时阈值。首页推荐还接入 Redis 缓存，缓存 Key 会区分用户和分页参数。

### 2. 路线规划

路线规划接口接收出发地、景点 ID 列表、出行方式、出行人群、预算和出行偏好。

主要步骤：

1. 从 MySQL 查询景点信息；
2. 对出发地和景点地址进行地理编码；
3. 优先使用景点已有经纬度，减少重复地理编码；
4. 调用高德路径服务计算景点之间的距离、时间和费用；
5. 构造路径成本矩阵；
6. 根据“经济、舒适或适中”选择时间和费用的权重；
7. 使用模拟退火搜索较优的景点访问顺序；
8. 组装路线结果并缓存。

模拟退火适合处理旅行商问题这类组合优化问题。它不保证在有限时间内得到绝对最优解，但可以通过接受部分较差解来跳出局部最优，通常比简单贪心排序更有探索能力。

成本函数可以抽象为：

```text
总成本 = 时间权重 × 总耗时 + 费用权重 × 总费用
```

路线规划使用独立线程池和超时控制，避免复杂计算长时间占用普通请求线程。景点数量过多会扩大矩阵和搜索空间，因此接口需要限制数量，并在超时时给出清晰提示。

### 3. 管理端与运营看板

管理端不是简单的“另一个前端页面”，它包含独立的管理业务：

- 景点、城市、类型和标签维护；
- 轮播图上传和排序；
- 用户和管理员管理；
- 角色与权限绑定；
- 操作日志查询；
- 用户行为和业务数据看板。

通过 RBAC，系统可以让不同管理员只拥有必要的操作权限，而不是所有后台用户都拥有全部能力。

## 五、性能设计

项目对几个容易变慢的环节进行了针对性处理。

### 1. 缓存策略

热点景点、推荐和路线结果优先从 Redis 返回；未命中时再访问数据库或执行计算，并设置过期时间。

### 2. 线程池隔离

推荐计算和路线规划使用不同的执行器。这样路线规划即使出现高耗时，也不会直接拖慢普通景点查询。

### 3. 超时控制

当前配置将推荐和路线规划设置为不同的超时时间。超时后快速失败，比无限等待更容易保护系统资源。

### 4. 数据库索引

`backend/sql/performance_indexes.sql` 针对用户行为、收藏、景点筛选和用户偏好等查询场景提供索引优化。索引应根据真实 SQL、数据规模和执行计划调整，不能只因为“加索引看起来更快”就无限添加。

### 5. 日志控制

生产配置默认关闭 MyBatis 标准输出 SQL 日志，以减少高流量环境中的 I/O 开销；排查问题时可以临时打开，但不建议长期打印大量 SQL 和敏感参数。

## 七、常见问题与排查思路

### 1. Lombok 与 JDK 版本不兼容

如果使用较新的 JDK 编译时出现 `ExceptionInInitializerError`、`com.sun.tools.javac.tree` 或 `Unsafe` 相关错误，先检查 Lombok 版本和 annotation processor 版本是否一致。当前项目已经显式指定 Lombok `1.18.42`。

### 2. 后端无法连接数据库

依次检查：

1. MySQL 是否启动；
2. 数据库名是否为 `travel_system`；
3. 用户名和密码是否正确；
4. 数据库端口是否为 `3306`；
5. 初始化脚本是否已经执行；
6. 环境变量是否被 IDE 或终端真正加载。

### 3. Redis 连接失败

检查 Redis 是否监听 `6379`，并确认后端的 Redis 主机、端口和密码配置。

### 4. 前端请求跨域或 401

检查：

- 前端 API 基础地址是否指向 `http://localhost:8080/`；
- Authorization 是否正确携带 Bearer Token；
- Token 是否过期；
- 后端 CORS 配置是否允许当前前端地址；
- 管理端 Token 是否确实是管理员 Token。

### 5. 路线规划速度慢

路线规划涉及地理编码、路径接口和组合优化。可以先减少景点数量，检查高德 API 配置和网络情况，再查看路线缓存是否命中。

### 6. 推荐结果不明显

新用户通常处于冷启动阶段，推荐会混合偏好和热门内容。登录用户需要产生足够的点击或有效停留行为，系统才会逐渐使用行为画像。

## 八、这个项目适合怎样学习

不建议一开始就试图读完所有源码，可以按下面的顺序学习：

1. 先运行用户端，了解页面和业务流程；
2. 从前端 API 文件找到一个接口；
3. 进入后端 Controller，查看请求 DTO 和返回 DTO；
4. 继续跟踪 Service、Mapper 和 Entity；
5. 再阅读该接口对应的缓存、权限和异步逻辑；
6. 最后阅读推荐和路线规划算法。

推荐选择一个完整链路进行分析，例如“景点详情”：

```text
Vue 页面
  → Axios API 模块
  → Spring Controller
  → Service
  → Redis 缓存
  → MyBatis-Plus Mapper
  → MySQL
  → DTO
  → 前端渲染
```

如果想练习后端，可以依次实现：

- 一个景点分页查询接口；
- 一个用户收藏接口；
- 一个管理员权限注解；
- 一个 Redis 缓存封装；
- 一个用户行为统计 SQL；
- 一个简单的推荐排序策略。

如果想练习前端，可以依次实现：

- Axios 请求拦截器；
- Pinia 用户 Store；
- Vue Router 登录守卫；
- Element Plus 表单和分页；
- ECharts 看板；
- SSE 流式消息显示。

## 九、项目中值得继续改进的地方

一个毕业设计项目的价值不在于宣称“已经完美”，而在于能够说明当前实现、边界和下一步方向。这个项目还可以继续改进：

1. 将所有敏感配置彻底迁移到环境变量或密钥管理服务；
2. 为 AI、地图和邮件服务增加更完整的重试、限流和熔断策略；
3. 用真实天气和人流量 API 替换路线结果中的预留数据；
4. 增加推荐离线评估指标，如点击率、覆盖率和多样性；
5. 对推荐和路线接口增加更系统的单元测试、集成测试和压测；
6. 对缓存更新建立更明确的一致性策略；
7. 对大规模景点和行为数据采用更适合的分页、归档或异步统计方案；
8. 生产环境关闭或保护 Swagger，并完善安全响应头、限流和审计策略；
9. 将 Python 数据脚本整理成可重复执行的数据处理流水线；
10. 增加 Docker Compose 或其他部署编排文件，降低环境搭建成本。

## 十、总结

这个项目展示了一个相对完整的全栈毕业设计应该包含哪些部分：

- Vue 3 + TypeScript 构建用户端和管理端；
- Spring Boot 提供 REST API 和业务服务；
- MyBatis-Plus 连接 MySQL 并组织数据访问；
- Redis 负责缓存、会话和高频数据；
- JWT 与 RBAC 处理身份和后台权限；
- 推荐算法利用显式偏好和隐式行为；
- 模拟退火与地图服务完成路线规划；
- SSE 和 OkHttp 支持流式 AI 旅游助手；
- AOP、Validation、OpenAPI 和线程池提升工程完整度；
- Python 和 SQL 脚本支撑数据准备与数据库维护。

对于大学生来说，最值得学习的不是照抄某一个框架，而是理解这些技术为什么被放在一起：页面解决交互，API 连接前后端，数据库保存事实，缓存降低访问成本，算法提供业务价值，权限和日志保证系统可治理，测试和配置则决定项目能否稳定运行。

希望这个项目和这篇文章能够给正在做毕业设计的同学一些可落地的参考：先把业务链路跑通，再逐步补齐安全、性能、测试和部署，最终形成一个自己真正理解、能够解释、也能够继续演进的系统。
